Novus 환경 및 처리 방식에는 여러분이 이해해야 할 몇 가지 중요한 측면이 있습니다.



[[novus-data-director-and-ontap-data-server-internal-communication]]
== Novus Data Director와 ONTAP 데이터 서버 내부 통신

Novus Data Director는 파일 액세스 및 관리를 지원하기 위해 ONTAP 데이터 서버와 통신합니다. 이러한 통신은 대부분 ONTAP 서버보다는 NDD에서 시작됩니다.



[[ontap-data-server-discovery]]
=== ONTAP 데이터 서버 탐색

Novus Data Director는 사용 가능한 데이터 서버가 무엇인지 탐색해야 합니다. ONTAP은 Novus Data Director와의 통신을 절대 시작하지 않습니다. 운영자 또는 툴은 시작 시 사용되는 `mds.conf` 구성 파일을 통해 각 데이터 서버를 등록합니다. 데이터 서버는 `mds-admin ds add` 명령을 사용하여 수동으로 추가할 수도 있습니다. 각 데이터 서버는 호스트, 엑스포트, 포트, 상태 및 용량 등을 포함하여 분산 메타데이터 저장소의 행으로 표시됩니다.



[[ontap-data-server-availability]]
=== ONTAP 데이터 서버 가용성

각 ONTAP 데이터 서버의 가용성을 확인하는 데에는 여러 가지 프로세스가 사용됩니다.

하트비트:: MDS는 TCP를 통해 각 온라인 데이터 서버로 NFSv3 NULL RPC 호출을 보냅니다. 기본적으로 하트비트 메시지를 사용하여 5초마다 이 작업을 수행합니다.
오프라인으로 전환하기:: 연속으로 일정 횟수 이상 오류가 발생하면 데이터 서버는 오프라인으로 표시됩니다. MDS는 더 이상 해당 서버에 새 파일을 배치하지 않고 클라이언트에게 해당 서버를 가리키는 레이아웃을 반환하도록 알립니다.
돌아오기:: 연속적으로 충분한 수의 성공적인 탐색이 이루어지면 온라인 상태로 복귀합니다. 쿨다운 기간은 상태가 반복적으로 전환되는 것을 방지합니다.
클라이언트 오류는 포함되지 않습니다:: 클라이언트가 오류를 보고하면 로그에만 기록됩니다. ONTAP 데이터 서버의 상태는 프로브만으로 판단됩니다.
ONTAP 페일오버는 보이지 않습니다:: ONTAP HA 쌍이 테이크오버를 수행하는 경우 MDS는 프로브 타임아웃을 통해서만 이를 감지합니다.




[[ontap-data-server-data-content]]
=== ONTAP 데이터 서버 데이터 콘텐츠

NDD는 ONTAP에 무엇을 저장하는지 묻지 않습니다. 모든 배킹 파일을 생성하기 때문에 이미 알고 있습니다:

* 파일이 생성되면 MDS는 데이터 서버를 선택하고 해당 서버에 백업 파일을 생성한 다음, 분산 메타데이터 저장소의 스트라이프 매핑에 결과를 저장합니다. 스트라이프 매핑에는 각 스트라이프와 미러를 보유하는 데이터 서버 및 NFS 파일 핸들이 기록됩니다.
* ONTAP의 백킹 파일은 NDD에서 특정 이름 형식을 갖습니다.
* 용량은 NDD가 마운트된 각 내보내기에 대해 statvfs()를 사용하여 ONTAP에서 읽는 유일한 운영 값입니다.
* 파일 크기는 ONTAP에 대해 검증되지 않습니다. 클라이언트의 레이아웃 커밋을 기준으로 결정됩니다.




[[high-availability-and-resiliency-for-the-ndd-cluster]]
== NDD 클러스터의 고가용성 및 복원력

Novus Data Director를 기반으로 하는 메타데이터 플레인은 시스템의 높은 가용성과 복원력을 보장합니다.



[[cluster-design]]
=== 클러스터 디자인

Novus는 NDD 서비스의 고가용성과 내결함성을 보장하기 위해 멀티 호스트 클러스터를 사용합니다.

장애 도메인이 3개 있는 호스트 3개:: 최소 NDD 클러스터 구성은 물리적 호스트 3대 또는 별도의 서버에 배포된 가상 머신(VM) 3대입니다. 각 호스트는 하나의 MDS 프로세스와 하나의 메타데이터 저장소 노드를 실행합니다. 이 클러스터는 호스트 하나에 장애가 발생하더라도 계속 작동하도록 설계되었습니다.
모든 복제본은 서비스합니다:: 모든 MDS 복제본은 대기 모드로 지정되지 않고 동시에 클라이언트를 처리합니다. 모든 정상 복제본은 BGP를 통해 동일한 VIP를 알립니다. BGP 자체 타이머만으로는 완벽한 장애 조치 메커니즘이 될 수 없으므로 BFD(고속 링크 장애 감지)가 필요합니다. 복제본은 NFS 서비스, 게이트웨이 및 메타데이터 저장소 연결이 모두 클라이언트 처리 준비가 완료된 경우에만 VIP를 알립니다.
메타데이터 복제:: 분산 메타데이터 저장소는 세 개의 동기식 복사본을 유지합니다. 중재자는 양측이 모두 쓰도록 허용하는 대신 비가용 상태로 전환하여 스플릿 브레인 상황을 방지합니다.
재시작은 안전합니다:: MDS 프로세스는 자체 상태를 유지하지 않습니다. 분산 메타데이터 저장소가 권위 있는 메타데이터를 보관합니다.




[[limitations-and-cautions]]
=== 제한 사항 및 주의 사항

다음과 같은 제한 사항 및 주의 사항에도 유의하시기 바랍니다:

* 서브트리 소유권은 자동으로 장애 조치되지 않습니다. 네임스페이스는 여러 서브트리로 분할될 수 있으며, 각 서브트리는 하나의 MDS가 소유합니다. 소유자에게 장애가 발생하면 VIP가 이미 이동했더라도 소유자가 복구될 때까지 해당 서브트리는 대기 상태가 됩니다.
* 각 테넌트가 호스트당 하나의 복제본을 가지고 있기 때문에 하나의 호스트 장애는 해당 호스트의 모든 테넌트에 영향을 미칩니다.
* 클라이언트는 호스트 IP가 아닌 VIP를 마운트해야 합니다. 그렇지 않으면 클라이언트가 페일오버를 수행할 수 없습니다.
* 하드 마운트는 복구 중에 차단될 수 있습니다. 마운트가 차단되었다고 해서 데이터가 손실된 것은 아닙니다.
* 유지보수는 항상 한 번에 하나의 복제본에 대해서만 수행하십시오. 먼저 VIP에서 복제본을 제외하고 드레인하십시오.
